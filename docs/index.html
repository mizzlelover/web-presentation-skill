Why · 为什么需要它

漂亮的页面 ≠ 有效的演示

AI 可以一分钟生成一份"看起来很炫"的 HTML 幻灯片——但它回答不了：面对什么人、在什么场景、为了什么目标，应该讲什么、删什么、先讲什么、何时揭示、何时深入。本系统先把这些问题答完，再谈渲染。

✕ 常见做法

  • 输入文档 → 直接生成 HTML，结构与视觉耦合
  • "每页最多 6 行""标题必须是问句"——没有证据的通用规则
  • 动画为了炫酷，3D 为了高级感
  • 线性翻页器，现场被打断就慌乱
  • 依赖 CDN，会议室断网即白屏

✓ 本系统

  • Strategy → IR → Renderer 强制管线，禁止一步到位
  • 规则带机制 / 证据分级 A–E / 边界条件；用户经验先登记为假设再验证
  • 语义动效：每个动效声明 Intent，讲者可暂停/跳转/跳过
  • Presentation Graph：核心路径 + Deep Dive + 证据附录 + 现场分支
  • 离线优先、三模式（Stage / Reader / Print）、打印可读
Pipeline · 六步工作流

从原始材料到演示应用

每一步都有独立的工件与质检门禁——IR 校验器不过，不允许进入渲染。

STEP 0

情境判定

20 类演示情境，Situation First；不同情境不同规则

STEP 1

受众建模

角色 / 决策权 / 态度 / 异议 / 认知负荷耐受，12 字段模型

STEP 2

论证架构

Thesis→Claim→Evidence 树，六查逻辑漏洞与过度声称

STEP 3

Scene 规划

每幕一个认知任务；标题类型由任务决定；负荷曲线有节奏

STEP 4

Presentation IR

声明式中间表示，validate_ir.py 强制校验

STEP 5

渲染 + QA

L0–L6 最低充分渲染；18 维评测；浏览器实测

Capabilities · 核心能力

一个 Skill，装下整个演示工程

🧭

情境 × 受众驱动

高管汇报、政务报告、技术评审、教学培训……20 类情境各有规则；同一份材料可为 CEO / 技术 / 一线生成三份明显不同的演示。

🧬

证据分级知识库

35+ 研究来源、A–E 证据分级、冲突证据显式登记；实践经验隔离在假设层，验证后才进入方法论。

🕸

非线性演示图

核心路径 / 可选路径 / Deep Dive / 证据附录 / 异议分支。现场被质疑？一键跳到证据幕，讲完原路返回。

🎛

讲者控制台

独立窗口：当前幕、下一幕、Speaker Notes、计时器、分支跳转。动画全部可暂停/回放/拖动——讲者永远控制节奏。

📖

三模式一模型

Stage 精简 / Reader 完整自足可深链 / Print 自动分页显示引用。同一份内容模型，三种视图，不做三遍。

🛡

对抗性设计

"字越少越好？""每页加动画？""全做 3D？"——系统按机制给出反对理由与替代方案，不盲从反方法论要求。

⚡

零依赖运行时

原生 JS 实现 Scene 引擎 / 动效控制 / 阅读模式 / 打印模式，无构建、无 CDN、断网可跑。Stable > Fancy。

📐

语义组件库

HeroStatement / AssertionEvidence / Comparison / Decision…组件是"信息结构"，不是模板；全部 tokens 化、响应式、可访问。

✅

评测与回归

18 维评分 rubric、100 测试案例、10 条对抗测试、IR 校验器、视觉/运行时 QA 清单——交付有门槛。
