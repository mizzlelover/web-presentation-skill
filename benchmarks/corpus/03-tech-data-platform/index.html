技术架构评审

中台不替换数据仓库，
而是补一层统一口径与统一服务

本次评审数据中台技术架构：只在三处引入新技术，其余复用既有资产。

（站定）先设边界，避免后面跑偏：中台不替换数据仓库。仓库继续做它的存储与计算，中台补的是两层东西——统一口径和统一服务。整套方案里真正的新东西只有三处，其余全部复用既有资产。接下来我按原则、架构、数据流、选型、集成、安全、落地七个部分展开，欢迎逐层打断。
本次评审数据中台技术架构：在既有数据仓库之上补「统一口径 + 统一服务」两层能力；仅引入三处新技术（元数据服务、指标服务、数据服务网关），其余复用既有资产。

依据：集团数据治理规划（内部）· 样例材料已脱敏

仓库有了，缺的是口径一致与访问一致

既有仓库解决了存储与计算；缺的是口径一致与访问一致。

仓库已解决DO NOT TOUCH

  • 结构化存储与分区
  • 批量 ETL 与调度
  • 历史数据留存

仍需补齐GAP

  • 指标口径唯一来源
  • 统一数据服务与鉴权
  • 血缘与影响分析
（指左栏）仓库解决了存储和批量计算，这部分不用动。（指右栏）问题是两个「不一致」：一是口径，同一个指标在不同报表里定义不一样，每月经营数据要人工核对；二是访问，各系统要么直连仓库，要么各自导出，没有统一的服务层，权限也散在各处。中台就是补这两件事。
既有数据仓库解决存储与批量计算。缺口：①口径不一致（同一指标多定义，需人工核对）；②访问不一致（各系统直连或自导出，无统一服务层，权限散落）。

来源：数据治理现状盘点（内部）

四条原则，第一条就是不动仓库

四条原则：不动仓库、只做薄层、能力可退、默认最小权限。

P1
不动仓库
不迁移、不重写既有 ETL。
P2
只做薄层
只承担口径与服务，不做新存储计算。
P3
能力可退
任一服务可下线，不影响业务取数。
P4
最小权限
服务层统一鉴权，按需授权。
（逐条）四条原则，第一条就是不动仓库——不迁移、不重写既有 ETL。第二，只做薄层，中台只承担口径和服务，不新增存储和计算。第三，能力可退，任何一个服务下线都不影响业务取数。第四，默认最小权限，服务层统一鉴权。（强调）这四条合起来，就是对「过度设计」的回答。
设计原则：①不动仓库；②只做薄层（不做新存储计算）；③能力可退（服务可下线）；④默认最小权限（服务层统一鉴权）。

来源：架构方案（内部）

架构四层，新增仅三处

四层架构：接入层、服务层、口径层、底座层；新增仅三处。

接入层（既有）
BI、报表平台、业务系统；通过网关统一取数。
服务层（新增）
数据服务网关 + 统一鉴权；对外只暴露服务接口。
口径层（新增）
元数据服务（血缘、定义）+ 指标服务（唯一口径计算）。
底座层（复用）
既有数据仓库与调度；不迁移、不重写。
（自上而下）四层。接入层是 BI、报表和各业务系统，全部既有。服务层是数据服务网关加统一鉴权，新增。口径层是元数据服务和指标服务，新增。底座层是既有仓库和调度，完全复用。（收）所以新增就是三处：网关、元数据、指标。
架构四层：接入层（BI/报表/业务系统，既有）；服务层（数据服务网关 + 统一鉴权，新增）；口径层（元数据服务 + 指标服务，新增）；底座层（既有仓库与调度，复用）。新增三处：网关、元数据服务、指标服务。

来源：架构方案（内部）

一次取数：口径从指标服务出，权限从网关过

取数链路：请求→网关鉴权→指标服务解析口径→仓库取数→返回并记血缘。

01
请求
BI / 报表 / 业务系统发起取数。
02
网关
统一鉴权、限流、审计。
03
指标服务
按唯一口径解析为查询计划。
04
仓库执行
既有仓库与调度执行查询。
05
血缘回报
结果返回并记录访问血缘。
（手指沿流程）一次取数：业务方发请求；网关做鉴权和限流；指标服务按唯一口径把请求翻译成查询计划；仓库执行；结果返回，同时把这次访问的链路记进元数据服务的血缘。（强调）全过程不允许绕过服务层直连仓库。
取数链路：请求 → 网关鉴权限流 → 指标服务解析唯一口径 → 仓库执行 → 结果返回并记录血缘；禁止绕过服务层直连仓库。

来源：架构方案（内部）

选型只看三条：成熟、可退、可自运维

选型标准：成熟、可退、可自运维。

组件选型理由新增/复用
元数据服务关系型存储 + 开源血缘模型可自运维、无外部依赖新增
指标服务既有 SQL 引擎不引入新执行引擎新增
数据服务网关既有网关注册扩展复用鉴权与审计插件新增
存储与调度既有数据仓库不迁移、不重写复用
（指标准）选型我们只看三条：成熟、可退、可自运维。（逐项）元数据服务用成熟关系型存储加开源血缘模型，理由是自运维、无外部依赖；指标服务基于既有 SQL 引擎，不引入新的执行引擎；数据服务网关在既有网关上扩展，复用现成插件和审计。三项都能本地离线部署，不依赖外部 SaaS。
选型：元数据服务=成熟关系型存储+开源血缘模型；指标服务=复用既有 SQL 引擎；数据服务网关=既有网关扩展。三项均满足成熟、可退、可自运维，且支持离线部署。

来源：技术选型说明（内部）

集成：三类系统，三种接法

三类系统三种接法：BI 直连服务、业务系统走接口、存量报表平移。

01
BI / 报表平台
改造取数连接串指向数据服务网关，应用侧改动最小。
02
业务系统
通过网关 REST 接口取数；不再开放数据库直连。
03
存量报表
分批平移；保留双跑期做口径比对，达标后切流。
（分类）三类系统三种接法。BI 和报表平台，改取数连接串指向网关，改动量很小；业务系统通过网关的 REST 接口取数，不再开放库直连；存量报表按批次平移，并且保留一段双跑期做口径比对。（补）第三类是集成成本的大头，所以给了双跑期。
集成：①BI/报表→改造连接串指向网关；②业务系统→走 REST 接口，禁止库直连；③存量报表→分批平移 + 双跑期口径比对。

来源：集成方案（内部）

权限模型：一人一角色、一数据一授权、全链路留痕

权限模型三条：角色化授权、数据级授权、全链路审计。

S1
角色化授权
按岗位定义角色；人员只挂角色，不逐人授权。
S2
数据级授权
敏感字段与数据域单独授权，默认拒绝。
S3
全链路审计
取数留痕：人、时间、口径、数据范围可回溯。
（面向安全）三条。角色化：按岗位定义角色，人只挂角色，不单独授权。数据级：敏感字段和数据域要单独授权，默认拒绝。审计：所有取数都经网关留痕，记录人、时间、用的哪个口径、拿了多大范围，事后可回溯。（收）安全口如果有额外要求，我们按最小必要原则再收紧。
安全：①角色化授权（人挂角色）；②数据级授权（敏感字段/数据域单独授权，默认拒绝）；③全链路审计（人、时、口径、范围可回溯）。

来源：安全方案（内部）

分三期落地，每期都有回退开关

三期：口径治理 → 服务上线 → 存量平移。

一期 · 0–3 月
口径与元数据
指标口径治理、元数据登记；不触碰线上链路。
二期 · 4–7 月
服务层上线
数据服务网关与指标服务上线；与旧路径双跑比对。
三期 · 8–12 月
存量平移
存量报表分批迁入；旧路径保留一季度后关闭。
（沿时间线）三期。一期零到三个月，先把口径治理和元数据登记做完——这一步不碰线上。二期四到七个月，网关和指标服务上线，与旧路径双跑比对。三期八到十二个月，存量报表分批平移，旧路径保留一个季度再关。（强调）每一期都有回退开关，任何一期出问题都能退回旧路径。
三期：一期（0–3 月）口径治理与元数据登记；二期（4–7 月）网关与指标服务上线 + 双跑比对；三期（8–12 月）存量报表平移，旧路径保留一季度。每期可回退。
