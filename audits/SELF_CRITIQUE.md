## 二、三个"看似完成、实则有水分"的大项

### 1. §53「10 份真实复杂中文材料」——名不副实（最严重）

**原文（真实研究补丁 §53）**：
> 至少准备：10 份真实复杂中文材料……**不得只用人工编造的几句话。**

**原文（真实研究补丁 §52）**：
> 测试：给系统一份**从未见过的真实内容**。不能依赖人工针对 Demo 调 CSS。必须通过 Strategy → IR → Renderer 自动生成合理结果。

**我的现状**：15 套 Deck 的 IR 全部是我**本人直接撰写**的。内容虽然做了脱敏、标注"样例"、
情节与数字自洽，但它们是**自撰合成材料**，不是从真实世界取得的输入（没有一份来自真实的
年报、政府公开文件、白皮书或用户实际项目文档）。

**这造成的连锁问题**：
1. §52 要求的"从未见过的真实内容"测试**从未执行**——因为我从未以"原始材料"为起点。
2. **§54 AI 生成流程的上半段没有工件**：Content Understanding → Goal Detection → Audience Model
   → Argument Architecture → Scene Planning 这五步只存在于 workflows 文档。corpus 里没有
   任何一份 `strategy` / `argument-map` / `scene-plan` 工件——而 §95 明确要求每组材料生成这七样。
3. **循环论证风险**：我既写了语料，又给语料的产出打分。语料无法再暴露"原始材料常见的
   脏、乱、缺、矛盾"问题（真实材料的典型特征恰恰是结构缺失、口径混乱、诉求不清）。
4. 第一份文档 §94 能力 **A（原始 Word/Markdown/长文 → HTML）**与 **C（提纲 → 完整演示）**
   因此属于**未验证**，而非此前暗示的"管线支持"。

**此前审计的虚标**：`CORPUS_COVERAGE.md` 标题写"真实复杂中文材料覆盖 10/10"。应更正为
"复杂中文材料（自撰合成样例）10/10；**真实世界材料 0/10**"。

### 2. §22 的九项 Evals —— 少了两维，且缺的两维恰恰最难

**原文（强制执行补丁 §22）**：必须执行 Strategy Eval、**Audience Adaptation Eval**、IR Eval、
Visual Eval、Runtime Eval、Browser Eval、Offline Eval、Performance Eval、Regression。

**我的现状**：`run_evals.cjs` 实现了 IR / Visual / Runtime / Browser / Offline / Performance /
Console 七维。**没有 Strategy Eval，也没有 Audience Adaptation Eval**。而且我的"IR Eval"
过弱（只数幕数与角色多样性），远不构成对 IR 质量的评价。

**更深的缺口**：第一份文档 §67 的 **100 个测试案例**仍是 designed（登记）而非 executed；
§66 的 **18 维 rubric 从未真正打分**；§68 的 **10 条对抗测试从未实际执行**——
即"用户说『所有数据做 3D』时 Skill 是否拒绝"这一类行为验证，目前只有人工自信，没有 eval 证据。

### 3. §96/§97「受众适配」——证明了"人能用手做"，没证明"系统能自动适配"

**原文（第一份文档 §96/§97）**：
> 输入同样的内容，系统是否真正能够针对不同受众、目标和场景产生**明显不同且合理**的演示策略。
> 必须证明"受众适配"：同一份材料 → CEO / Technical / Frontline。

**我的现状**：derived/ 的三受众版本**是我手写差异化**的。这证明"该系统**能承载**三种合理策略"，
但没有证明"**系统能自动推导**出三种策略"——后者依赖 §54 上半段（受众模型 → 策略）的实现。
严格按原文判据，§96/§97 为**部分达成**。

## 三、语料库与信源是否足以保证质量？——直接回答：**不足以**

### 语料

| 维度 | 现状 | 原文要求 | 判定 |
|---|---|---|---|
| 数量 | 15 套（10 基准 + 5 衍生） | ≥10 | ✅ |
| 类型 | 10 类全覆盖 | 10 类 | ✅ |
| **来源性质** | **自撰合成样例** | 真实复杂材料，"不得人工编造" | ❌ **不满足** |
| **输入形态** | 直接写 IR | 原始材料（Word/长文/提纲/数据）→ 全管线 | ❌ **不满足** |
| 工件完整性 | 仅 IR + HTML | Strategy + Argument Map + Scene Plan + IR + Runtime + Reader + Print（§95） | ❌ 缺前三样 |
| 消费方 | 我自己 | "从未见过的真实内容"（§52） | ❌ |

### 信源

| 维度 | 现状 | 风险 |
|---|---|---|
| 广度 | 58 条来源登记，覆盖 10 个学科域 | 够用 |
| 深度 | 13 个证据包声称"全文精读" | **这些精读是由上一手执行者完成的，我本人未复核任何一篇** |
| 状态分布 | 53 节点中 26 partially_validated / 22 memory_based / 5 engineering_validated | 无虚标 VALIDATED（这点是干净的），但 22 个 memory_based 意味着四成节点只是"登记了来源的常识" |
| 可复核性 | 证据包内记录了效应量与结论 | **未做抽查复核**：若某包的数字或结论与原文有出入，引用它的节点会继承错误 |
| 外部评审 | 无 | 全部自产自评 |

**结论**：广度够、深度不保证、复核缺失。当前证据链是"信任传递"而非"已验证传递"。

## 五、修复顺序（按对方法论成立的影响排序）

**P0-1 真实语料注入 + 上游管线工件化**（直接救 §52/§53/§94A/C/§95）
- 取 3 份真实材料起步：①用户实际项目文档的脱敏版（免税商城方案 / 可研请示件）；
  ②一份真实上市公司年报或政府公开文件；③一份真实技术白皮书或标准文本。
- 为每份产出完整工件链：`content-understanding.md → strategy.yaml → argument-map.yaml →
  scene-plan.yaml → presentation.ir.json → index.html`，并新增
  `validate_strategy.py`（校验 strategy/argument-map/scene-plan 的结构与引用一致性）。
- 成功判据：**换一份我从未参与撰写的真实材料，不改 Renderer/组件 CSS，产出合格 Deck。**

**P0-2 补齐 §22 的 Strategy Eval 与 Audience Adaptation Eval**
- Strategy Eval：对同一材料的多受众版本做**结构差异断言**（幕数、信息密度分布、术语表、
  内容取舍、认知任务序列必须系统性不同，且差异方向符合受众模型）。
- 目前 derived/ 三版本的差异是手写的——eval 要做的是把"差异"变成可测断言，防止未来退化。

**P1-1 证据包抽查复核**
- 抽 3–5 个证据包（覆盖 A 级与 B 级），重新获取原文，逐条核对包内引用的效应量与结论；
  复核结果写入 TRACEABILITY_MATRIX；无法复核的包降级并标注。

**P1-2 数据 fallback（§3/§16）**
- echarts 缺失/加载失败时，chart block 渲染为内置 HTML 表格（数据语义兜底），并实测。

**P1-3 18 维 rubric 实跑**
- 对 15 套 Deck 执行 18 维评分，标注"单评审、无外部校准"的局限。

**P2**
- 对抗测试 10 条实跑（人工执行 + 记录）；对比度/字号/alt 自动检查脚本；
  §20 的 25 条规则中未机器化的条目逐条落进 validate_ir/renderer。

## 六、结语

此前的交付在**工程下游**是诚实的：渲染器、运行时、三模式、离线、打印、自动化验证、
真机 Safari 都是真实做出来、真实测过的，缺陷也是真修的。

但在**方法论的根**上，这份检讨必须承认两件事：
1. **语料是我写的**——所以"15 套 Deck 全绿"证明的是"系统能渲染我写的内容"，
   还不能证明"系统能消化真实世界的烂摊子"。
2. **证据是继承的**——我复核过它们的存在性与自洽性，没有复核过它们的真实性。

这两件事不补上，"方法论成立"就还差一口气。上面的 P0 两项是补上这口气的最短路径。
